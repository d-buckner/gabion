# Framework Spec (working title: TBD)

Status: DRAFT v0 — decisions marked [OPEN] need sign-off.
Inspired by Dune (xAI Grok Bot client architecture): agents take shortcuts, so the
shortest path must be the correct path. Enforcement is mechanical (crate graph,
compile targets, lint gates), never a standard the author has to remember.

## 1. Goal

Build single-binary Rust apps where the same business logic runs:

1. natively (CLI + native renderer),
2. in the browser as wasm (renderer + in-process core),
3. on a server (HTTP API + MCP),

with zero duplication of business logic. Every service operation is automatically
available as a CLI subcommand, an HTTP endpoint, an MCP tool, and a typed client
call — generated from one definition. All four are built (§5).

## 2. Non-goals (v1)

- Not a UI framework, and not a design system. The framework ships no components, no
  tokens and no styles (`framework-ui` enforces it); Dioxus is what the examples use,
  because it is the only mature native+wasm stack. [OPEN: confirm renderer-agnostic vs
  bundled]
- Streaming is **decided** (open question 4 below): stream ops land in v1, the
  policy carried by the return type, duplex as a listen op plus an ordinary send
  op, served on **one WebSocket per host** whose frames are namespaced by feature.
  Per-stream flow control over that shared connection is v2, and SSE stays out of
  v1. [streaming.md](streaming.md) is the decision; none of it is built yet.
- No mobile targets.
- Not a web framework replacement: axum/rmcp/clap are used internally, not rebuilt.

## 3. The load-bearing decision (DECIDED: Option B)

The service core is **pure and target-agnostic**. It compiles for
`wasm32-unknown-unknown` and native. No tokio, no std::fs/net/time/thread inside
core. All effects (clock, storage, network, sleep, randomness) are capability
traits with per-target implementations supplied by the host.

Consequence: the compile target is one wall, but not the one this draft first
claimed. `std` ships wasm stubs for `std::fs`, `std::net`, `std::thread` and
`std::time`, and tokio's `rt` feature builds on `wasm32-unknown-unknown` — all
verified on the pinned toolchain — so a core that reaches for `std::fs`
**compiles for wasm**. The mechanical seal is two audits instead: `clippy.toml`
enumerates the banned paths (`disallowed_types` / `disallowed_methods`, audited
by `clippy-config`), and `core-runtime-dep` reads every `*-core` manifest and
refuses a runtime, server, client, or storage crate. The wasm build still runs,
because it catches a dependency that genuinely cannot build there (tokio's `net`
via mio, C-linked libraries). Enumerated lists have edges; GAPS §3 records the
ones that remain.

## 4. Layout: feature-first, sealed per feature (Dune colocation, Rust enforcement)

Two orthogonal walls, both enforced by the crate graph (not lints):

- **Process wall** (Dune: main vs renderer): render <-> core. Render may only
  import the feature's `api` crate — and, for composition, another feature's
  `render` crate (its published components), never its `core`.
- **Feature wall** (Dune: feature colocation + cross-feature import ban):
  feature A may import feature B's `api` only — never B's `core` or `render`.

```
myapp/
├── Cargo.toml                          # workspace (PLANNED: members generated by `gabion feature add`)
├── platform/                           # framework runtime + app-wide shared code
│   ├── gabion/  gabion-macros/  gabion-cli/      # (see §9)
│   └── myapp-shared/                   # cross-cutting types: Id<T>, Money, Page<T>, AppError
├── features/
│   └── todo/                           # EVERYTHING about todo lives here — one folder
│       ├── todo-api/                   # wire types + #[service] trait (compiles everywhere)
│       ├── todo-core/                  # impl of the trait; pure; depends: todo-api, shared, gabion
│       └── todo-render/                # UI components; depends: todo-api, shared, gabion, ui kit
└── hosts/
    ├── myapp-host-native/              # bin: CLI + native renderer (in-process cores)
    ├── myapp-host-server/              # bin: axum (MCP + wasm bundle: PLANNED)
    └── myapp-host-web/                 # cdylib: wasm renderer (HTTP client: PLANNED)
```

A host may be split across more than one binary. `example/hosts/host-pulse-cli`
and `host-pulse-native` are two hosts over the same cores (CLI and desktop window),
and `host-pulse-web` is a third (wasm) — the split is a composition decision, not
an architecture one. `ui kit` above means third-party UI crates; the edge table
only audits workspace members.

### Why 3 crates per feature instead of 3 modules

Cargo.toml dependencies ARE the import ban: a crate can only `use` what's in its
`[dependencies]`. With module-per-feature you'd need arch-lint to police
`use crate::todo::core::...` from render code; with crate-per-feature the import
is unrepresentable. `gabion feature add todo` generates the boilerplate, so the
colocation cost is zero for humans and agents. Compile time is fine: api crates
are types-only and fast; cargo parallelizes small crates.

### Allowed edges (gabion check audits every Cargo.toml against this table)

| Crate            | May depend on                          |
|------------------|----------------------------------------|
| X-api            | gabion, shared, other features' *-api      |
| X-core           | X-api, shared, other features' *-api   |
| X-render         | X-api, other features' *-render (component composition), shared, gabion — NOT any *-core |
| hosts            | all *-core + *-render (composition only), plus an effect home |
| effect home      | gabion, shared, other features' *-api — never a *-core or a *-render |
| shared           | gabion only — never any feature            |

An effect home is where an app's own effects live: a pty, a serial port, a C
library. gabion names one by the `-native` suffix or by a line in
`[workspace.metadata.gabion] effect-homes`, and a host is an effect home too. It
gets the effect bans lifted and it may not reach another feature's logic or UI, so
wiring effects into a contract stays a host job. A crate named `host-native` is a
host written in native code, not an effect home: the host test runs first.

Cross-feature calls: todo-core may depend on billing-api and receive billing's
client — in-process today, HTTP once the generated client is built (GAPS §4) —
never billing's internals. This is Dune's "features
talk through their public surface" rule, made physical, and
`example/features/incidents` is the working case: `incidents-core` depends on
`checks-api` and nothing from `checks-core`, and it reads probe history through
the same `CheckService` trait an HTTP client walks through.

### Registration (BUILT: `mount_on`, not `linkme`)

`#[service]` emits an inherent method on the trait object:

```rust
impl dyn CheckService + Send + Sync {
    pub fn mount_on(self: Arc<Self>, host: &mut gabion::registry::Host) { /* … */ }
}
```

so a host names the impl and nothing else — no namespace, no router function, no
tool list:

```rust
let mut host = Host::new();
checks.mount_on(&mut host);
incidents.mount_on(&mut host);
let app = gabion_native::host_router(&mut host);
```

`Host::mounted()` / `contracts()` / `exposed()` / `exposed_routes()` make what a
running process serves an artifact a test can pin. `exposed()` names every
operation; `exposed_routes()` names only the `POST /api/<ns>.<op>` routes, because
a listen op is served on `GET /api/ws` instead. The original plan here was a
`linkme` distributed slice; it was built and measured **empty** in a real host
binary (the linker is free to drop the object file holding an rlib static), which
is the fail-open class GAPS §1 bans, so the linker is not involved. The method
version also works on wasm, which the slice version could not (GAPS §7).

What runtime registration cannot see is an *absent* call, so `gabion check` owns
that direction: `unserved-contract` fails when a `#[service]` trait is named by no
host crate. `gabion check` also verifies the Cargo.toml edge table, so a
hand-added forbidden dep fails CI naming the wall rule.

DTOs live in `*-api`, not `*-core`. If an agent puts a DTO in core, render gets
an immediate compile error pointing at the wall — the error message is the
documentation.

## 5. The contract: one trait, four surfaces

```rust
// features/todo/todo-api/src/lib.rs
use gabion::prelude::*;

#[derive(Serialize, Deserialize, JsonSchema)]
pub struct CreateTodo { pub title: String }

// one error enum -> HTTP status and CLI exit code, through ErrorKind
pub enum TodoError { NotFound, EmptyTitle, Internal }

#[service]                   // generates the router, the clap subcommand, and
                             // the OpenAPI 3.1 document for both
pub trait TodoService {                 // the trait IS the boundary:
    /// Add one todo. Fails with `EmptyTitle` when the title is blank.
    async fn create(&self, input: CreateTodo) -> Result<Todo, TodoError>;
    async fn list(&self, q: ListQuery) -> Result<Vec<Todo>, TodoError>;
}

// DECIDED: no per-method surface attributes. Every method in a #[service] trait
// is generated into every surface. An op that must not be remote lives outside
// the trait — a plain trait here for cross-feature in-proc calls:
pub trait TodoInternals {
    async fn recompute_stats(&self) -> ();
}
// ...or an inherent method on the impl in todo-core, reachable by nothing
// outside the feature. Adapters hold Arc<dyn TodoService>, so neither is
// reachable from any surface. Structure, not lint.
```

Because there is no attribute to review, the reviewable artifact is the *set* of
reachable operations: `gabion check` locks it in `.gabion/surfaces.lock` and
fails when it drifts, so "this method is now callable by an agent" appears as a
diff in the PR rather than in production.

`#[service]` generates, feature-gated so each host compiles only what it needs.
All six rows are built; the notes record the shape each one took:

| Feature    | Generated artifact                          | Note |
|------------|---------------------------------------------|------|
| (default)  | `<Feature>Client<H: Http>`: the service trait implemented over `Http` | The in-process surface needs no generated code: the trait object *is* the in-process client, so a renderer takes `Arc<dyn TodoService>` and cannot tell which it was handed. |
| `registry` (default) | `mount_on` on the trait object     | §4. Not `linkme`, and it works on wasm. |
| `server`   | axum routes                                 | `POST /api/{feature}.{method}`. |
| `server` + `openapi` | OpenAPI 3.1 document for exactly those routes | |
| `mcp`      | one JSON-RPC tool per method                | `gabion::mcp`, not `rmcp`: the three methods this framework uses are the three it has to test, and the error mapping is the interesting part. Served over stdio and `POST /mcp`. No SSE in v1. |
| `cli`      | clap subcommand mapping                     | Global `--principal` / `--tenant` / `--trace`. |
| `conformance` | `<ns>_conformance(svc, http, base, cases)` | §8. |

The document is gated on the router feature on purpose: a contract cannot
describe a route that is not served. It is built from the same types the handlers
deserialize, and the method's doc comment becomes the operation's summary, so
there is one source for the route, its shape, and its prose. The app commits the
output and a test fails when the code and the committed document disagree.

The renderer takes `Arc<dyn TodoService>` from its host and calls
`client.create(&ctx, input)`, so the signature, the types and the errors are the
same on every target — and so is the caller, because `Ctx` is the first parameter
of every method (decision 1). Whether the host injected the core or the generated
`TodoClient` is invisible to the screen: `host-web` shows both postures off one
trait object. This is the Dioxus `#[server]` dual-codegen pattern, generalized to
four surfaces and enforced by the crate wall.

Wire format: JSON, one POST per method (`POST /api/todo.create`; `route()` in
`gabion-macros` is the single place the path is computed), args as the body, the
bare return type on `200`, and a flat `WireError` carrying the error's status on
failure (decision 2 below). OpenAPI is exported from the same source for public
API docs and external codegen. [OPEN: CBOR/MessagePack as option for wasm payload
size]

## 6. Capabilities (effects)

```rust
// crates/gabion/src/caps.rs — what exists today
pub trait Caps: Clone + Send + Sync + 'static {
    type Clock: Clock;    // fn now(&self) -> Timestamp (whole seconds, on purpose)
    type Store: Store;    // async key-value of JSON strings
    type Random: Random;  // fn next_u64(&self) -> u64; ids need entropy, not luck
    type Sleep: Sleep;    // fn sleep(&self, ms) -> Timer; fn timer(&self, ms) -> Timer
    type Http: Http;      // fn send(&self, HttpRequest) -> Result<HttpResponse, HttpError>
    // fn sleep(&self) -> &Self::Sleep; fn http(&self) -> &Self::Http;
}

pub struct TodoServiceImpl<C: Caps> { caps: C }
impl<C: Caps> TodoService for TodoServiceImpl<C> { /* business logic */ }
```

- Core is `async` but runtime-free: it returns futures; hosts drive them
  (tokio native, JS event loop on wasm). No tokio dependency in core.
- Native host wires `NativeCaps` / `FileCaps` (`SystemClock`, in-memory or
  file store, `SystemRandom` over getrandom, `TokioSleep`, `ReqwestHttp`).
- Tests wire `TestCaps`: a virtual clock that moves only when code waits,
  in-memory store, deterministic `MockRandom` — which is what makes
  id-dependent behaviour reproducible rather than flaky — `MockSleep`, and
  `MockHttp` with scripted routes. `gabion::caps::timeout` bounds a wait on
  whichever clock the capability carries.
- Web hosts wire a capability bundle chosen by the host. `host-pulse-web` wires
  the real `WebCaps` (js Date, localStorage, js crypto, `setTimeout`, `fetch`),
  so its cores run in the page; `host-web` (todo) still wires `TestCaps`
  (mock clock/store/random/sleep/http) as a wasm wall proof only.
- `Store::set_as(&ctx, ..)` carries the caller on a write, so an implementation can
  record who wrote a row (`FileStore` keeps a `<path>.writers.json` sidecar).
- Storage v1: abstract `Store` trait; `FileStore` is the shipped native impl
  (pure Rust, no C deps keeps the single-binary promise). It loads the file once
  and keeps the map in memory, rewriting on each mutation, so a screen that asks
  for one watch's history per row is a map lookup rather than a re-parse of the
  whole store. redb/sqlx left to the app.

## 7. Lint rulebook (Dune-style: ban the shortcut, not the person)

Each row: a shortcut an agent (or tired human) will take -> the mechanical block.

| Shortcut | Block |
|---|---|
| render imports any core | crate graph; unrepresentable (process wall) |
| a feature UI reaching into another feature's *internals* | `over-broad-visibility`: `pub` in a `*-render` is a published component, and anything no other crate names must be `pub(crate)`. Composing another feature's UI is allowed and expected; reaching past its components is a finding. |
| feature A imports feature B's core/render | crate graph; unrepresentable (feature wall) |
| hand-edit Cargo.toml to sneak a forbidden dep | `gabion check` audits every Cargo.toml against the edge table |
| shared depends on a feature (upward leak) | same edge-table audit |
| `std::fs`, `std::net`, `std::thread`, `std::time`, `std::env`, `std::process` in any `*-core` | `clippy::disallowed_types` / `disallowed_methods` deny, audited by `clippy-config`. The wasm target does **not** catch these: `std` ships wasm stubs, so they compile and fail at runtime. |
| `tokio`, `axum`, `reqwest`, `sqlx`, … in a `*-core` manifest | `core-runtime-dep` reads the manifest. tokio's `rt` feature builds for wasm, so the target would not catch it. |
| effect without capability | same as above |
| DTO defined in core | render compile error at the wall |
| a service trait implemented in a host crate | `host-business-logic`. Hosts may define wiring helpers; they may not implement a `*Service` trait. |
| forgetting to expose an op | the trait is the boundary: any method in a `#[service]` trait is on every surface, so there is nothing to forget |
| publishing an op by accident | `surface-snapshot`: `.gabion/surfaces.lock` must match the reachable method set |
| a `#[service]` trait declared outside `*-api` | `service-outside-api`: `#[service]` generates surfaces wherever it is written, so the lock scans every crate, and a trait in the wrong crate is named |
| hand-written HTTP handler bypassing contract | `axum-outside-host`: any `axum` path in a non-host app crate is a finding. Reads paths, not types, so a re-export slips past it (GAPS §3). |
| `unwrap()` / `expect()` | `clippy::unwrap_used`, `expect_used` deny, workspace-wide. `panic` and `implicit_clone` are not banned. |
| unsafe anywhere outside effects | `unsafe_code = "forbid"` in `[workspace.lints.rust]`, audited by `workspace-lints` |
| a member that skips the workspace wall | `workspace-lints`: every member must carry `[lints] workspace = true`, or the block is inert for it |
| over-broad visibility (`pub` past the wall) | `over-broad-visibility`: a `pub` item in a `*-core` that no other crate names is a finding, and `--fix` narrows it to `pub(crate)`. The decidable direction only (GAPS §3). |
| a published contract no host mounts | `unserved-contract`: the registry cannot see an absent call, so the gate checks that a host crate names the trait. |
| a workspace with no `*-core` | `no-wasm-proof`, so the wasm step cannot pass having built nothing. |
| glob re-exports across the wall | `contract-glob`: a `pub use` whose tree contains a glob is a finding in any `*-api` crate. clippy's `wildcard_imports` is not the wall here: it does not lint `pub use` globs (measured on rust 1.99). |
| code comments in service bodies (Dune's ban) | `no-comments-in-service-bodies` in `gabion check`: no comments inside `*-core` fn bodies; `///` docs on public items stay required (codegen needs them) |
| silent default on a failed read/write | `core-silent-default`: `unwrap_or_default()` / `unwrap_or(..)` on a `Result` in `*-api` or `*-core` is a finding — a corrupt row must fail loudly, not vanish |
| a `TODO` / `FIXME` / `XXX` | `no-todo` |
| an over-long file or over-wide function | `file-length` (400), `too-many-branches` (10); clippy's cognitive 15, lines 80, args 6 |
| deleting the wall instead of fixing the code | `clippy-config` and `workspace-lints`: `gabion check` audits `clippy.toml` and `[workspace.lints]` themselves; a removed ban, a loosened threshold, or a lowered lint level is a named finding |
| `#[allow]` smuggled into a pure crate | `allow-allowlist`: `clippy::disallowed_*` allows are legal only in a declared effect home |

Delivery (built): the gate is `gabion-cli`, run as `cargo run -p gabion-cli --
check`. It orchestrates `rustfmt`, `clippy` (workspace lints + `clippy.toml`),
`cargo test`, `cargo shear`, `cargo deny`, and a wasm build of every `*-core`,
then adds the rules above that need gabion's shape. The edge table is data in
`[workspace.metadata.gabion.edges]`, not code, so an app can widen its own walls
without patching the framework. CI template: `.github/workflows/ci.yml`.
The point stands: `gabion check` green == architecture correct, so an agent with
zero context cannot pass CI while violating the wall.

Two deliberate deviations from the original plan:

- **No hand-rolled linter.** The first draft of this spec assumed a bespoke
  arch-lint. A handful of rules turned out to need gabion-specific knowledge —
  the edge table, the surface lock, effect-home allows, and the source-shape
  rules that clippy cannot express (core comments, silent defaults, TODOs,
  `core-runtime-dep`, `contract-glob`); everything else is delegated to tools
  that already exist and are better maintained than we will be. Clippy's `too_many_branches` is the one exception: its threshold is
  hardcoded at 42, so the branch cap lives in `gabion check` instead.
- **Uniform thresholds across crate classes** (cognitive 15, lines 80, args 6,
  branches 10, type-complexity 150) rather than tiered limits per layer.

## 8. Verification story (verification > generation, per Tan)

- Core is pure -> deterministic unit tests with `MockCaps` (fixed clock, in-memory store).
- Generated conformance suite: `<ns>_conformance(svc, http, base, cases)` drives
  one input through the impl, the generated clap tree, the generated MCP tool and
  the generated client over a socket, and compares the four answers as JSON —
  including the failure envelope, which is why the CLI now carries the same
  `WireError` the route sends. A case the suite cannot drive is a rejection, not a
  pass. It cannot compare a *create*: two calls are two creates, so the cases are
  the ones a repeat answers the same way (GAPS §8).
- UI snapshots: every published panel is rendered from fixture data and compared
  against a committed file in `.gabion/ui/` (text for the string view, HTML through
  `dioxus-ssr` for components). The UI counterpart of the OpenAPI snapshot: a
  component that keeps its props and changes what it shows is a diff someone reads.
- `gabion check` = fmt + clippy + test + shear + deny + wasm-target build of
  core + the gabion-specific rules. One command, one exit code.
- The gate is dogfooded: `crates/gabion-cli/tests/dogfood.rs` runs the real
  checker over this repo, and `tests/rules.rs` proves each static rule fires on
  a fixture that violates it (individual fixtures, plus `every_rule_bites` for
  the rulebook at once). A rule without a failing fixture is the same trap as a
  README claiming a wall that isn't there.

## 9. Framework's own crates

```
gabion/         # runtime: prelude, client traits, error model, capability traits
gabion-macros/  # #[service]: cli, server, openapi, mcp, client, registry, conformance
gabion-native/  # native caps: SystemClock, FileStore (a declared effect home)
gabion-cli/     # `gabion check`, `gabion new`, `gabion feature add`, `gabion dev`
gabion-codegen/ # openapi export, contract snapshot (reviewable generated diff) [still one crate's
                # job inside the macro; a separate crate is not built and is not needed yet]
```

`gabion dev` builds, runs, watches sources and restarts, so the agent loop stays
fast — which is half of Dune's thesis. It runs one host binary; a wasm renderer is
started by the app's own bundler script, because which one that is is a host
decision.

## 10. Decisions

Signed off in the v0.1 audit:

1. **Per-call context is an explicit `Ctx` parameter** (principal, tenant,
   trace-id, cancellation) on every service fn, not a scoped service or a
   task-local. It is visible in the contract, trivially testable, and the
   generated adapters construct it. This deliberately breaks the "exactly one
   input argument" shape — accepted. **Built**: `ctx: &Ctx` first on every
   method, filled in by HTTP headers, MCP `_meta`, CLI flags and the client's own
   headers; cancellation is a flag plus a waker list, so the runtime stays
   wasm-safe.
2. **Errors round-trip via a separate `WireError` plus `From`-style
   conversions.** Built. The in-proc error stays rich (thiserror-style typed
   detail); the wire type is flat and bidirectional, and `ErrorKind` is
   serialized instead of `#[serde(skip)]`. Conversions are generic runtime impls
   rather than per-service codegen.
3. **wasm browser posture: thin client over HTTP, or local-first.** The render
   crate may be handed the generated `TodoClient` so core does not run in the
   browser;
   `host-pulse-web` instead runs the same cores over `WebCaps` (localStorage +
   `fetch`), which keeps the board usable offline-first and needs no server.
   Which one an app takes is a host decision, not a framework one.
4. **Dune's comment ban is adopted, scoped to `*-core` fn bodies.** Doc comments
   on public items stay required — codegen and OpenAPI read them.
5. **The trait is the boundary; there are no per-method surface attributes.**
   Every method in a `#[service]` trait is generated into every surface. Ops
   that must not be remote live outside the trait: a plain trait in `*-api` for
   cross-feature in-proc calls, inherent methods on the impl for
   feature-local internals. There is no opt-out for one surface — if it must not
   be remote, it is not in the trait. The reviewable artifact is the locked set
   of reachable ops (`.gabion/surfaces.lock`), not an annotation per method.

Still open (see `docs/GAPS.md` for the full log, ordered by how much damage the
silence does):

1. Renderer: agnostic + Dioxus template (recommended) vs bundled renderer stack.
2. Wire format: JSON-only v1 vs CBOR option.
3. Name (needs registry + SERP collision sweep before publishing).
4. ~~Streaming surfaces: `Stream` return support — v1 or v2?~~ — **decided: v1**.
   The policy is a return-type marker rather than a per-method attribute, duplex is
   a listen op plus an ordinary send op in one namespace, and the transport is one
   feature-namespaced WebSocket per host. [streaming.md](streaming.md) holds the
   design, the stages, and the failing tests that have to land with it.
5. ~~Whether `gabion check` should grow a `--fix`~~ — decided and built: it
   applies the findings that carry an exact text edit (a narrowed `pub`, the
   surface lock) once, and leaves the rest for a human.

## 11. Cheapest experiments first

1. Spike the walls: hand-write two features (todo, billing) x api/core/render +
   one host. Prove: render cannot import core, todo-core cannot import
   billing-core, and the wasm build of a core fails on `std::time`.
2. Spike `#[service]` v0: macro that generates just the axum router + clap from
   the trait (skip mcp/client first). Prove one fn -> two surfaces compiles.
3. Add rmcp + Http client stub. Add `gabion check`. **Done, with one deviation:**
   `gabion check` exists, is tested against negative fixtures, and runs in CI; the
   HTTP client and MCP surface are built, but on `gabion::mcp` rather than `rmcp`
   (§5).
4. Only then: `gabion new` scaffolding + Dioxus template. **`gabion new`,
   `gabion feature add` and `gabion dev` are built**; the Dioxus template is not
   (the scaffold's renderer prints, and a Dioxus screen is a host decision).
