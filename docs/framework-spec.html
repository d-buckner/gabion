One business core. Four surfaces.
Shortcuts mechanically sealed.

A Rust framework for single-binary apps whose business logic runs natively, in the browser as wasm, and on a server — exposed automatically as CLI, HTTP API, MCP tools, and a typed client. Inspired by Dune, the Grok Bot client architecture: agents take shortcuts, so the shortest path must be the correct path. Enforcement is mechanical — crate graph, compile targets, lint gates — never a standard the author has to remember.

DRAFT v0 DECIDED · pure core (Option B) 6 open decisions rust · wasm32 · axum · rmcp · clap

01Goal

Build single-binary Rust apps where the same business logic runs:

  • natively — CLI + native renderer, core in-process
  • in the browser as wasm — renderer + in-process core (local-first)
  • on a server — HTTP API + MCP

with zero duplication of business logic. Every service operation is automatically available as a CLI subcommand, an HTTP endpoint, an MCP tool, and a typed client call — generated from one definition.

02Non-goals (v1)

  • Not a UI framework. The renderer is pluggable; Dioxus is the recommended default (only mature native+wasm UI stack). [OPEN: renderer-agnostic vs bundled]
  • No streaming/SSE surfaces in v1 (contract shape reserved for it).
  • No mobile targets.
  • Not a web framework replacement: axum / rmcp / clap are used internally, not rebuilt.

03The load-bearing decision

Decided — Option B The service core is pure and target-agnostic. It compiles for wasm32-unknown-unknown and native. No tokio, no std::fs/net/time/thread inside core. All effects (clock, storage, network, sleep, randomness) are capability traits with per-target implementations supplied by the host.

The rejected alternative (Option A) kept the core server-only and shipped a wasm UI over HTTP — Dioxus fullstack's model. It's simpler, but then "works natively and for web" means the UI works everywhere, not the app. Option B makes the web build a real runtime for the business logic: local-first is possible, and the same core is testable with zero I/O.

Key insight The compile target itself is the strongest lint. A service fn that reaches for std::fs compiles natively and fails on wasm — the shortcut is mechanically sealed, not reviewed.

04Layout: feature-first, sealed per feature

Dune's other half is colocation: everything about a feature lives in one folder, and cross-feature imports are blocked except through a feature's public surface. Two orthogonal walls, both enforced by the crate graph (not lints):

  • Process wall (Dune: main ↔ renderer): render may only import the feature's api crate — never core internals.
  • Feature wall (Dune: cross-feature import ban): feature A may import feature B's api only — never B's core or render.

Why 3 crates per feature instead of 3 modules

Cargo.toml dependencies are the import ban: a crate can only use what's in its [dependencies]. With module-per-feature you'd need arch-lint to police use crate::todo::core::… from render code; with crate-per-feature the import is unrepresentable. fw feature add todo generates the boilerplate, so colocation costs nothing for humans or agents. Compile time is fine: api crates are types-only and fast; cargo parallelizes small crates.

Allowed edges (fw check audits every Cargo.toml against this table)

CrateMay depend on
X-apifw, shared, other features' *-api
X-coreX-api, shared, other features' *-api
X-renderX-api, shared, ui kit — NOT any *-core
X-renderX-api, other features' *-render (components), shared, fw — never a *-core
hostsall *-core + *-render (composition only)
sharedfw only — never any feature

Cross-feature calls: todo-core may depend on billing-api and receive billing's client (in-proc or HTTP) — never billing's internals. Dune's "features talk through their public surface" rule, made physical.

The same holds one layer up: todo-render may depend on billing-render and mount its components, never billing's private sub-components — pub in a render crate is the published surface, and over-broad-visibility fails the gate for a public item nothing outside names. Composing two features on one screen is the normal case, so the edge exists; reaching past a feature's components is a finding, so the wall moved rather than disappeared.

Registration without wiring #[service] emits mount_on on the trait object, so a host writes checks.mount_on(&mut host) and gets the routes, the subcommand and the tools with zero manual registration. (The first version used a linkme distributed slice; it was measured empty in a real host binary, because the linker may drop the object file holding an rlib static — GAPS §1. The method form cannot be silently absent, and it works on wasm.) An agent adds a feature folder and it appears in all four surfaces. fw check audits the Cargo.toml edge table, so a hand-added forbidden dep — the agent "shortcut" — fails CI with a message naming the wall rule violated. DTOs live in *-api, not *-core: put one in core and render gets an immediate compile error pointing at the wall — the error message is the documentation.

05The contract: one trait, four surfaces

// features/todo/todo-api/src/lib.rs
use fw::prelude::*;

#[derive(Serialize, Deserialize, JsonSchema)]
pub struct CreateTodo { pub title: String }

#[derive(FwError)]            // one error enum -> HTTP status, MCP error, CLI exit code
pub enum TodoError { #[code(404)] NotFound }

#[service]                   // generates client, router, clap, mcp, openapi
pub trait TodoService {
    #[surface(cli, http, mcp)]
    async fn create(&self, input: CreateTodo) -> Result<Todo, TodoError>;

    #[surface(cli, http)]
    async fn list(&self, q: ListQuery) -> Result<Vec<Todo>, TodoError>;

    #[internal]              // explicit opt-out; required or surface-completeness lint fails
    async fn recompute_stats(&self) -> ();
}

The renderer calls client.create(&ctx, input). On native that's an in-process call; on web it's a POST to the server. Same signature, same types, same errors, same caller — Ctx is the first parameter of every method, and each surface fills it in. The in-process surface needs no generated code: the trait object is the in-process client, so a renderer cannot tell which it was handed. This is the Dioxus #[server] dual-codegen pattern, generalized to four surfaces and enforced by the crate wall.

MCP is served by gabion::mcp (JSON-RPC 2.0 over stdio and POST /mcp) rather than rmcp: the three methods this framework uses are the three it has to test, and the error mapping — ErrorKind to JSON-RPC code — is the interesting part. No SSE stream in v1.

Wire format: JSON, one POST per method (POST /api/todo.create), args as body, Result<T, E> envelope. OpenAPI exported from the same source for public API docs and external codegen. [OPEN: CBOR/MessagePack option for wasm payload size]

Delivery The framework ships fw-lints (preset clippy config + arch-lint.toml + cargo-deny.toml) and fw check runs the full gate set in one command. CI template generated by fw new. The point: fw check green == architecture correct, so an agent with zero context cannot pass CI while violating the wall.

08Verification story

Verification, not generation, is the bottleneck (Tan). Agents prove work by execution, not review.

  • Core is pure → deterministic unit tests with MockCaps (fixed clock, in-memory store).
  • Generated conformance suite: one case is driven through all four adapters (in-proc, clap dispatch, MCP tool call, generated client over a socket) and the four answers are compared — including the failure envelope, so an adapter that drops the kind or the detail fails. A case the suite cannot drive is a rejection, not a pass. It cannot compare a create: two calls are two creates, so the cases are the ones a repeat answers the same way.
  • UI snapshots: every published panel is rendered from fixture data and compared against a committed file in .gabion/ui/ — text for the string view, HTML through dioxus-ssr for components. The UI counterpart of the OpenAPI snapshot, so a component that keeps its props and changes what it shows is a diff someone reads.
  • A streaming return is a compile error with a reason, until streaming is decided: four generated surfaces cannot carry a Stream, and the author used to get an E0038 from code they did not write.
  • fw check closes its own gaps: over-broad-visibility, axum-outside-host, unserved-contract, no-wasm-proof, a signature hash in the surface lock, tests/ scanned by the shape rules, and --fix for the findings that carry an exact text edit.

09Framework's own crates

fw/            # runtime: prelude, client traits, error model, capability traits
fw-macros/     # #[service], #[surface], #[FwError]
fw-codegen/    # openapi export, contract snapshot (reviewable generated diff)
fw-lints/      # presets + `fw check` driver
fw-cli/        # `fw new`, `fw dev` (native+server+web hot reload), `fw check`

fw dev runs server + wasm renderer + native CLI against one workspace with one command — the agent loop stays fast, which is half of Dune's thesis.

10Open decisions

recommended

1 · Renderer

Agnostic + Dioxus template vs bundled renderer stack. Lean: agnostic — Dioxus is the only mature native+wasm UI.

lean: local-first

2 · Web posture default

Local-first (core in wasm) vs thin client over HTTP. Both supported per-app; pick the scaffold default.

lean: JSON-only

3 · Wire format

JSON-only v1 vs CBOR option for wasm payload size.

lean: skip

4 · Dune's comment ban

Adopt for service bodies? Doc comments on trait fns feed MCP tool descriptions — that's shortest-path-is-correct.

blocked

5 · Name

Needs registry + SERP collision sweep before publishing.

lean: v2

6 · Streaming

Stream return support in the contract — v1 or v2?

11Cheapest experiments first

  1. Spike the walls. Hand-write two features (todo, billing) × api/core/render + one host. Prove: render cannot import core, todo-core cannot import billing-core, and the wasm build of a core fails on std::time.
  2. Spike #[service] v0. Macro generating just the axum router + clap from the trait (skip mcp/client first). Prove one fn → two surfaces compiles.
  3. Add rmcp + Http client stub. Add fw check. Done, with one deviation: the MCP surface and the HTTP client are built, on gabion::mcp rather than rmcp.
  4. Only then: fw new scaffolding + Dioxus template.
